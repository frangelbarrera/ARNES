    10→
    11→## 1. Resumen ejecutivo
    12→
    13→ARNES tiene **una arquitectura elegante** (stateless reducer + specialists + middleware + playbooks YAML) y **buenas intenciones** documentadas. Pero la implementación actual tiene **patrones de IA rotos en producción** que los tests unitarios **no detectan** porque el `MockLLMProvider` devuelve JSON que no conforma ningún schema y los tests sólo verifican `success is True`.
    14→
    15→Los 5 problemas estructurales que bloquean alpha:
    16→
    17→1. **El VerificationLayer es marketing en producción.** El `output_schema` declarado en cada `SpecialistConfig` **nunca se pasa** al `VerificationLayer` (sólo se pasa `response_format`). La validación de schema está muerta. Los tests que la prueban la llaman directo, bypasseando el Specialist.
    18→2. **No hay tool-use loop (ReAct).** Los specialists declaran `tools=["fs_read", "fs_write", "shell"]` pero `Specialist.run()` **ignora completamente** esa lista. Un @coder no puede leer el código existente antes de escribir el nuevo. Son prompt templates, no agentes.
    19→3. **El executor tiene bugs semánticos graves:** `saltar_a` (jump-to) está implementado como skip (se salta el destino), los outputs de pasos paralelos no se resuelven en templates (`pasos.paralelo.lint.salida` queda literal), y los templates multi-`{{ }}` sólo resuelven el primero.
    20→4. **Doble wrapping de middleware.** `Agent.run()` y `Specialist.run()` **ambos** envuelven el provider con `TokenOptimizer → VerificationLayer → CostGuard`. Resultado: 2 caches, 2 verification layers, 2 CostGuards con presupuestos independientes. El CostGuard interior se crea fresh por invocación → **nunca acumula spend entre pasos**.
    21→5. **El default `ollama/llama3.2` no puede producir los structured outputs que los system prompts exigen.** Llama 3.2 3B/8B sin fine-tuning de JSON mode produce outputs parcialmente válidos con frecuencia alta. Combinado con el bug #1 (sin validación de schema), el sistema silenciosamente acepta JSON malformado y lo reporta como `success: True`.
    22→
    23→Adicionalmente hay **~25 issues** de severidad media/baja que se detallan en §3.

    27→## 2. Respuestas a las 10 preguntas
    28→
    29→### 2.1 ¿Los system prompts de los specialists son buenos?
    30→
    31→**Veredicto: Aceptables pero desiguales.** No son malos, pero tienen anti-patrones.
    32→
    33→**Lo bueno:**
    34→- Tienen estructura clara: job → rules → schema de salida.
    35→- Las "Rules" son específicas y anti-vaguedad ("'Review the code' is bad, 'Review PR #123 for security vulnerabilities' is good").
    36→- @debugger y @reviewer tienen metodología explícita (bottom-up traceback reading, severity ranking).
    37→- Tienen temperature bien calibrada (0.0 para código/review, 0.1 para planning).
    38→
    39→**Anti-patrones detectados:**
    40→
    41→- **Inconsistencia EN/ES:** Los system prompts están 100% en inglés, pero los playbooks (`manuales/*.yaml`) están en español y el `_inject_refusal_prompt` está en inglés. El LLM recibe mensajes mezclados. Para un framework bilingüe, esto es ruido.
    42→- **El schema embebido en el prompt no coincide con el `output_schema` declarado.** Ejemplo: el prompt del @coder dice `{"files": [...], "summary": ..., "assumptions": [...], "warnings": [...]}` pero el `output_schema` sólo requiere `["files", "summary"]`. El LLM ve un schema rico en el prompt pero el sistema sólo valida lo mínimo. Inconsistencia que confunde.
    43→- **@tester asume ejecución de tests** (`test_results.passed`, `failed`) pero no tiene forma real de ejecutarlos (no hay tool-use loop). El prompt le pide "Run the tests" pero el specialist no puede hacerlo.
    44→- **@reviewer está sobrecargado:** se usa para leer diff (`leer_diff` en auditar-pr), para auditoría de seguridad (`auditoria_seguridad`), para lint, y para síntesis. Especialización falsa.
    45→- **@coder y @tester declaran `tools=["fs_read", "fs_write", "shell"]` pero el prompt no les dice cómo usarlos** ni cuándo. Como no hay tool-use loop (bug #2), esto es decorativo.
    46→- **No hay instrucciones de formato robustas.** Ningún prompt dice "Return ONLY the JSON, no prose before or after". Llama 3.2 frecuentemente añade ```json ... ``` fences o texto explicativo, rompiendo el `json.loads`.
    47→
    48→### 2.2 ¿El Verification Layer realmente previene alucinaciones?
    49→
    50→**Veredicto: NO. Es marketing en el estado actual.**
    51→
    52→Hay **tres bugs** que lo inutilizan en producción:
    53→
    54→**Bug A (CRITICAL): El `output_schema` nunca llega al VerificationLayer.**
    55→
    56→En `specialists/base.py:115`:
    57→```python
    58→response = await guarded_provider.complete(
    59→    messages,
    60→    model=model,
    61→    temperature=...,
    62→    max_tokens=...,
    63→    response_format={"type": "json_object"} if self.config.output_schema else None,
    64→    # ← NUNCA se pasa response_schema=self.config.output_schema
    65→)
    66→```
    67→
    68→El `VerificationLayer.complete()` acepta `response_schema` como kwarg, pero el Specialist nunca lo pasa. Resultado: en `verification.py:144`, la condición `if self.config.structured_outputs and response_schema:` siempre es `False` porque `response_schema is None`. **La validación de schema es dead code en producción.**
    69→
    70→Los tests en `test_middleware.py:86` pasan porque llaman directo a `verification.complete(..., response_schema={...})`, bypasseando el Specialist.
    71→
    72→**Bug B (HIGH): Hedging detection con falsos positivos.**
    73→
    74→Los patrones en `verification.py:32-39`:
    75→```python
    76→r"\bI\s+don'?t\s+know\b",
    77→r"\bI'?m\s+not\s+sure\b",
    78→r"\bas\s+an\s+ai\b",
    79→```
    80→
    81→Se aplican al **contenido completo** del response (que es JSON). Si el @reviewer devuelve honestamente `{"summary": "I'm not sure about the auth flow"}` — el patrón `I'm not sure` matchea, la verificación falla, y el response se reemplaza por el `refusal_message` (string plano, no JSON). Luego `Specialist._parse_output()` hace `json.loads(refusal_message)` → falla → retorna `{"raw": refusal_message}` con `success: True`. **El sistema reporta éxito con un string de rechazo como output.**
    82→
    83→Peor: el prompt del @reviewer dice "If the code is good, say so. Don't invent issues." — incentiva honestidad, pero el VerificationLayer castiga la honestidad.
    84→
    85→**Bug C (HIGH): `confidence` es hardcoded a 0.8.**
    86→
    87→En `verification.py:131`:
    88→```python
    89→result = VerificationResult(passed=True, confidence=0.8)  # default
    90→```
    91→
    92→No hay ningún mecanismo que extraiga la confianza real del LLM. El `confidence_gate` (v0.2 placeholder) no sirve de nada porque la confianza nunca baja de 0.8 excepto si hay hedging (0.4) o validation failure (0.0).
    93→
    94→**¿Qué pasa si el LLM devuelve JSON válido pero factualmente incorrecto?**
    95→
    96→**Nada.** El VerificationLayer sólo valida forma (JSON parseable, campos requeridos), no contenido. Un @debugger que devuelva `{"root_cause": "wrong guess", "confidence": 0.9, "fix": {...}}` pasa todas las validaciones. El critic loop (v0.3) y grounding RAG (v0.4) están documentados pero no implementados.
    97→
    98→El único check factual existente — hedging detection — produce falsos positivos (Bug B).
    99→
   100→### 2.3 ¿El Token Optimizer hace routing correcto?
   101→
   102→**Veredicto: La heurística es defectuosa y puede degradar calidad silenciosamente.**
   103→
   104→Regla en `token_optimizer.py:30-35`:
   105→```python
   106→_ROUTING_RULES = [
   107→    (500, False, "ollama/llama3.2"),       # tiny input, no tools → local
   108→    (2000, False, "anthropic/claude-3-5-haiku-20241022"),
   109→]
   110→```
   111→
   112→**Problemas:**
   113→
   114→1. **"input < 500 tokens → ollama" rompe el caso de uso principal.** Si el usuario pagó por Claude Sonnet 4 y lanza un @planner con input corto (típico: `{"task": "Plan JWT auth"}` ~10 tokens), el router lo downgradeará a ollama/llama3.2 **sin avisar**. El usuario paga por premium y obtiene output de llama 3.2 3B.
   115→2. **La estimación `len(content) // 4` es mala para JSON.** Un input como `{"traceback": "...", "files": [...]}` con 200 chars reales puede tener 80 tokens (más del 25% del límite de 500). La heurística subestima, no sobreestima.
   116→3. **La regla "no tools" es ALWAYS TRUE en producción** porque el Specialist nunca pasa `tools` (bug #2: no hay tool-use loop). Entonces el routing siempre evalúa → siempre downgrades si input < 500 tokens.
   117→4. **Caso que rompe:** @reviewer con input corto `"Review this function: def add(a,b): return a+b"`. 20 tokens. Routing → ollama. Llama 3.2 responde `{"verdict": "approve", "issues": [], "summary": "looks good"}`. El usuario esperaba un review serio de Claude. Silencioso.
   118→5. **`_is_more_expensive` es frágil.** Match por substring: `"gpt-4o"` está en tier 2, pero `"gpt-4o-mini"` también contiene `"gpt-4o"` → max(tiers) = 2. Funciona por accidente, no por diseño.
   119→6. **La decisión de routing no se persiste en el Thread.** El `MODEL_ROUTED` event type existe pero nunca se emite. Inobservabilidad.
   120→
   121→**Casos que rompe:**
   122→- Input corto + modelo premium pagado → downgrade silencioso a ollama.
   123→- Input que crece entre turnos (multi-turn) → cambia de modelo mid-conversation.
   124→- JSON denso (poco texto, muchos tokens) → subestimación.
   125→- Cualquier specialist con `default_model="ollama/llama3.2"` (todos, actualmente) → routing nunca se activa porque el modelo pedido ya es ollama.
   126→
   127→### 2.4 ¿El cache del TokenOptimizer es semánticamente correcto?
   128→
   129→**Veredicto: Correcto para inputs idempotentes, peligroso para todo lo demás.**
   130→
   131→**Lo correcto:**
   132→- La cache key incluye messages + model + tools + kwargs (excepto temperature). Es determinista.
   133→- TTL de 1h es razonable.
   134→- LRU eviction OK.
   135→
   136→**Lo peligroso:**
   137→
   138→1. **No sabe nada de tiempo.** Si un playbook pregunta "What's the latest PR in this repo?" y se corre dos veces en 1h, la segunda devuelve respuesta stale.
   139→2. **No sabe nada de estado de usuario.** Si el input incluye `"user_id": 123` y el estado del usuario cambia entre llamadas, la cache devuelve respuesta vieja.
   140→3. **No sabe nada de turnos previos en el Thread.** El cache key incluye los `messages` completos, así que si el sistema prompt cambia, miss. Pero si el sistema prompt NO cambia y sólo el contexto del Thread (que NO está en messages) cambia, hit erróneo. **Esto es sutil pero crítico:** el @reviewer en paso 4 de un playbook puede recibir el mismo input literal que en paso 2 pero en un contexto distinto — la cache le devuelve la respuesta de paso 2.
   141→4. **Cachea respuestas del @planner con `temperature=0.1`** — planificación pseudo-aleatoria. Si dos runs idénticos devuelven outputs distintos (por temp), el segundo obtiene el output del primero. Inconsistencia.
   142→5. **`cached.response` es mutado in-place** al marcar `usage.cached = True` (línea 98). Eso viola el supuesto de immutabilidad del `LLMResponse` y puede causar bugs sutiles si el mismo objeto cached se devuelve múltiples veces.
   143→6. **No hay invalidación por cambio de código/schema.** Si cambias el system prompt del @coder, la cache sigue devolviendo respuestas con el prompt viejo hasta que expire el TTL.
   144→7. **Cache hits no emiten evento `CACHE_HIT`** (el event type existe pero no se usa).
   145→
   146→**Recomendación:** Desactivar cache por default para specialists no-idempotentes (@planner, @debugger). Activar sólo para @coder/@tester cuando el input es idéntico Y la temperature es 0.0.
   147→
   148→### 2.5 ¿El CostGuard maneja edge cases?
   149→
   150→**Veredicto: Funciona para happy path, falla en 4 edge cases.**
   151→
   152→**Edge cases que falla:**
   153→
   154→1. **LLM no reporta usage → `response.usage` es None → crash.**
   155→
   156→   En `litellm_provider.py:98-100`:
   157→   ```python
   158→   usage = response.usage
   159→   tokens_in = usage.prompt_tokens if usage else 0
   160→   tokens_out = usage.completion_tokens if usage else 0
   161→   ```
   162→   Esto maneja `usage is None` OK. Pero en `cost_guard.py:181`:
   163→   ```python
   164→   cost = response.usage.cost_usd
   165→   ```
   166→   Si el proveedor devuelve un `LLMResponse` con `usage=None` (no el caso actual pero plausible con providers custom), esto crashea con `AttributeError`. Falta defensive check.
   167→
   168→2. **Cost es 0 (Ollama/Mock) → CostGuard NUNCA aborta.**
   169→
   170→   Con ollama, `cost_usd=0.0` siempre. Entonces `self.spent_usd` siempre es 0. Entonces `self.spent_usd >= effective_budget * self.budget.abort_at_pct` (0 >= 0.50) es `False` siempre. **El "killer differentiator" de ARNES es no-op para el modelo default.**
   171→
   172→   El circuit breaker tampoco dispara porque `recent_spend` siempre es 0.
   173→
   174→   **Implicación:** Con el stack default (ollama), un playbook con loop infinito corre para siempre sin abortar por costo. Sólo aborta por `max_attempts` (no implementado en executor) o timeout (tampoco).
   175→
   176→3. **Retries no se deduplican.** Si un call falla y se reintenta, ambos costs se suman. Esto es correcto (fuiste cobrado), pero el `RetryPolicy` está definido en el schema y **nunca se usa en el executor**. Los retries simplemente no existen en v0.1.
   177→
   178→4. **Pause_at_pct es no-op.**
   179→
   180→   En `cost_guard.py:146-157`:
   181→   ```python
   182→   if self.spent_usd >= effective_budget * self.budget.pause_at_pct:
   183→       self._paused = True
   184→       logger.warning("cost_guard_pause", ...)
   185→       self._paused = False  # ← immediately unpauses!
   186→   ```
   187→
   188→   El comentario dice "In MVP we don't auto-pause; we let the call go through but warn." Pero la lógica de `_paused` que se setea y desetea en la misma rama es código muerto. Si algún caller verifica `_paused`, nunca verá True. **El HITL gate documentado no existe.**
   189→
   190→5. **Doble CostGuard.** El `Agent.run()` envuelve con `CostGuard(provider, budget=CostBudget(task_budget_usd=self.config.budget_usd))` y luego pasa ese wrapped provider a `specialist.run()`, que lo vuelve a envolver con `CostGuard(VerificationLayer(TokenOptimizer(...)))`. El CostGuard interior usa `CostBudget()` default (task=$0.50), empieza con `spent_usd=0` y se recrea en cada invocation. **Nunca acumula spend entre invocaciones.** Es peso muerto.
   191→
   192→### 2.6 ¿Los playbooks de ejemplo son útiles?
   193→
   194→**Veredicto: Como demostración de DSL, OK. Como playbooks funcionales, NO.**
   195→
   196→**`debug-python-issue.md.yaml`:**
   197→
   198→- `leer_traceback` llama a `@debugger` con el traceback inline. OK conceptualmente.
   199→- `revisar_fix` pasa `codigo: "{{ pasos.leer_traceback.salida }}"` a `@reviewer`. Pero `leer_traceback.salida` es un dict `{"root_cause": "...", "confidence": ..., "fix": {...}, ...}` — **no es código**. El @reviewer recibe un JSON de diagnóstico como si fuera código y se le pide revisarlo. Output será basura o el reviewer alucinará que el JSON es código.
   200→- `verificar_tests` pasa el mismo output del debugger como `codigo` al `@tester`. El tester espera código para escribir tests, recibe diagnóstico. Mismo problema.
   201→- **No diagnosticaría un bug real.** El @debugger solo ve el traceback inline; no puede `fs_read` el archivo referenciado (`src/app.py` línea 42) porque no hay tool-use loop. Propone un fix a ciegas.
   202→
   203→**`auditar-pr.md.yaml`:**
   204→
   205→- `leer_diff` usa `@reviewer` con `enfoque: "Leer el diff y estructurarlo"`. Pero @reviewer está diseñado para **revisar** código, no para **leer y estructurar** un diff. Necesita un `@lector-de-diff` que no existe (se menciona en docstrings pero no está registrado).
   206→- `auditoria_seguridad` también usa `@reviewer`. El reviewer no tiene tools de security scanning ni instrucciones específicas de security en su prompt (sólo menciona "Flag security issues explicitly" como una de las cosas a revisar). No es un auditor de seguridad real.
   207→- El paso `paralelo` se ejecuta secuencialmente (bug documentado en executor).
   208→- `sintesis` referencia `{{ pasos.paralelo.lint.salida }}` y `{{ pasos.paralelo.tests.salida }}`. Pero el executor guarda parallel outputs como `outputs["paralelo"] = {"lint": <output>, "tests": <output>}`. El template `pasos.paralelo.lint.salida` se traduce a `outputs["paralelo"]["lint"]["salida"]` → no existe (`salida` no es key del output directo). **El template queda como string literal** y el @reviewer de síntesis recibe `"{{ pasos.paralelo.lint.salida }}"` como texto. Bug confirmado empíricamente.
   209→
   210→**`write-feature-tdd.md.yaml`:**
   211→
   212→- Flujo TDD correcto conceptualmente (plan → tests → código → review → verificar).
   213→- Pero el `@coder` recibe `tests: "{{ pasos.escribir_tests.salida }}"` y `spec: "Implement JWT auth to make the tests pass"`. Sin tool-use loop, el coder no puede ejecutar los tests ni iterar. Escribe código a ciegas y ora que pase.
   214→- `verificar_tests_pasan` llama a `@tester` con `enfoque: "Run the tests"`. El tester no puede correr tests (no tool-use loop). Va a inventar `test_results: {"passed": 5, "failed": 0}` sin haber corrido nada. **Alucinación incentivada por el prompt.**
   215→
   216→**`hola-mundo.md.yaml`:**
   217→
   218→- Usa `@coder` para "Write a markdown outline". El system prompt del @coder dice "Write production-quality code, not pseudo-code" y exige "type hints, docstrings". Aplicar eso a un markdown outline es absurdo. Falta un `@writer` specialist.
   219→
   220→### 2.7 ¿Falta algo crítico?
   221→
   222→**Sí, mucho.**
   223→
   224→1. **Tool-use loop (ReAct).** Es EL patrón que diferencia un agente de un prompt template. Los specialists declaran tools pero no las usan. Sin esto, @coder no puede leer código existente, @tester no puede correr tests, @debugger no puede reproducir el bug. **Blocker para alpha.**
   225→2. **Streaming.** No hay. Para playbooks largos (auditar-pr), el usuario espera minutos sin feedback. UX inaceptable para alpha público.
   226→3. **Multi-turn / conversación.** No hay. Cada `specialist.run()` es single-shot. No hay forma de decirle al @coder "no, that's wrong, try again" dentro de un mismo step.
   227→4. **Memory persistente.** No hay. Cada run empieza desde cero. No hay learning entre runs. Un @debugger que vio un bug similar ayer no lo recuerda.
   228→5. **Retry con backoff.** `RetryPolicy` está definido en el schema pero **nunca se usa** en el executor. Un transient error (rate limit, timeout) mata el run entero.
   229→6. **Timeout por step.** `timeout_s` está en el schema pero no se usa. Un LLM colgado corre para siempre (hasta el httpx timeout de 120s en ollama).
   230→7. **HITL real.** `HITLGate` y `aprobacion_humana` están en el schema pero el executor no los enforcement. `HumanApprovalTool` existe pero no se llama automáticamente.
   231→8. **Tool calling nativo.** `LLMProvider.complete()` acepta `tools` pero ni ollama ni litellm provider los pasan correctamente al modelo. Ollama provider dice "tool use is evolving — fall back to text parsing" pero no hay parser de texto.
   232→9. **Structured output con pydantic.** El `output_schema` es JSON Schema declarativo pero nunca se valida con pydantic en runtime. Debería ser `Type[BaseModel]` y validar el response contra él.
   233→10. **Observabilidad.** Los eventos `MODEL_ROUTED`, `CACHE_HIT`, `CONFIDENCE_SCORED`, `REFUSAL_TRIGGERED` existen en el enum pero no se emiten. Inobservabilidad total del middleware.
   234→
   235→### 2.8 ¿El default a ollama/llama3.2 es realista?
   236→
   237→**Veredicto: NO para los structured outputs que piden los specialists.**
   238→
   239→**Hechos sobre Llama 3.2:**
   240→- Llama 3.2 viene en 1B y 3B (small) y 11B/90B (vision). Los que corren en ollama default son 1B y 3B.
   241→- Llama 3.2 3B puede producir JSON simple con `format: "json"` en ollama, pero:
   242→  - Frecuentemente añade ```json fences o texto explicativo antes/después del JSON.
   243→  - No respeta schemas anidados (e.g., `files: [{path, language, content, action}]`).
   244→  - Confunde `action: "create"` con `action: "create_new"` o `action: CREATE`.
   245→  - Trunca outputs largos (el @coder con 200 líneas de código se corta).
   246→  - Alucina imports y APIs (el prompt del @coder dice "Never invent APIs" pero Llama 3.2 lo hace).
   247→
   248→**Lo que va a pasar en alpha:**
   249→- @planner devuelve `{"steps": [{"id": "step-1", "specialist": "@coder", "input": {...}}]}` — a veces válido, a veces con `steps` como string en vez de array.
   250→- @coder devuelve JSON con `files` como string en vez de array de objetos. `_parse_output` hace `json.loads` exitoso pero el output no es utilizable.
   251→- @reviewer devuelve `verdict: "Approve"` (capitalizado) en vez de `"approve"` — no está en el enum, pero como el schema no se valida, pasa.
   252→- @debugger propone fixes plausibles pero incorrectos con `confidence: 0.9`.
   253→
   254→**Recomendación:** Default a `ollama/llama3.2` está bien para el quickstart "hola-mundo". Para `write-feature-tdd`, `debug-python-issue`, `auditar-pr` el default debería ser `anthropic/claude-3-5-haiku-20241022` (barato, structured outputs fiables) o `groq/llama-3.3-70b-versatile` (gratis, más capaz que 3.2 3B).
   255→
   256→Alternativamente: añadir un `_clean_json_response()` post-proceso que strippe fences y extraiga el primer `{...}` válido. Eso subiría el success rate de 60% a ~85% con Llama 3.2.
   257→
   258→### 2.9 ¿La separación specialist/tool/playbook es correcta?
   259→
   260→**Veredicto: Separación conceptual correcta, acoplamiento indebido en implementación.**
   261→
   262→**Lo correcto:**
   263→- Specialist = (system_prompt + tools + output_schema). Data class, no hierarchy. ✔
   264→- Tool = (Args + Result schemas + execute()). Auto-registrado. ✔
   265→- Playbook = YAML → DAG. Compiler + executor separados. ✔
   266→- Thread = event log immutable. ✔
   267→
   268→**Acoplamiento indebido:**
   269→
   270→1. **El Specialist base hardcodeda el middleware stack.** En `base.py:99-105`:
   271→   ```python
   272→   optimized_provider: LLMProvider = TokenOptimizer(provider)
   273→   if self.config.output_schema:
   274→       optimized_provider = VerificationLayer(...)
   275→   guarded_provider = CostGuard(optimized_provider)
   276→   ```
   277→   El Specialist decide el orden del middleware. Pero el `Agent.run()` y el `PlaybookExecutor` también envuelven con CostGuard. Resultado: doble wrapping. **El middleware stack debería vivir en UN lugar** (el executor o el agent, no el specialist).
   278→
   279→2. **El executor pasa `cost_guard` como `provider` al specialist.** Tipo: `provider: cost_guard,  # type: ignore[arg-type]`. El `# type: ignore` es admission de que el type system no soporta esto. `CostGuard` no es un `LLMProvider` (no hereda). Funciona por duck typing. Frágil.
   280→
   281→3. **`ToolContext` tiene `budget_remaining_usd` que se calcula del CostGuard del executor, pero el specialist tiene su propio CostGuard que no se lo pasa.** El tool no ve el budget real.
   282→
   283→4. **Los specialists referencian tools por nombre string** (`tools=["fs_read"]`), no por tipo. Si renombras `fs_read` a `filesystem_read`, todos los specialists se rompen silenciosamente (no validation en registry).
   284→
   285→5. **El `SpecialistRegistry` se auto-registra via `__init_subclass__`** — frágil al orden de imports. Si `get_default_specialist_registry()` se llama antes de que se importen todos los módulos de specialists, el registry está vacío. Funciona ahora porque el import está inline en la función, pero es un piegun.
   286→
   287→6. **Los playbooks referencian specialists por nombre** (`especialista: "@reviewer"`). Si un specialist se renombra, el playbook compila OK pero falla en runtime con "Specialist not registered". El compiler check debería verificar referencias (como hace con `saltar_a`).

   289→### 2.10 ¿Hay bugs en el executor? ¿El template resolution funciona? ¿Los condicionales?
   290→
   291→**Veredicto: Sí, hay 5 bugs significativos.**
   292→
   293→**Bug 1 (CRITICAL): `saltar_a` está invertido.**
   294→
   295→En `executor.py:455-459`:
   296→```python
   297→if branch.accion == "saltar" and branch.saltar_a:
   298→    # Mark target steps to be skipped until saltar_a
   299→    skip_set = outputs.setdefault("__skip_steps", set())
   300→    skip_set.add(branch.saltar_a)  # Will be cleared when we reach it
   301→```
   302→
   303→`saltar_a: "step-5"` significa "saltar A step-5" (jump TO step-5). Pero el código añade `step-5` al skip set, lo que hace que step-5 se **skip**. Semántica invertida.
   304→
   305→Además, el comentario "Will be cleared when we reach it" miente — nunca se clear. Una vez en el skip set, se queda para siempre. Y no hay lógica de "skip steps BETWEEN current y target" — sólo se skippea el target.
   306→
   307→**Fix correcto:** Si step-3 tiene `saltar_a: step-5`, hay que skippear step-4 (los pasos intermedios) y ejecutar step-5. Implementación:
   308→```python
   309→if branch.accion == "saltar" and branch.saltar_a:
   310→    target_idx = next(i for i, s in enumerate(playbook.pasos) if s.id == branch.saltar_a)
   311→    current_idx = next(i for i, s in enumerate(playbook.pasos) if s.id == step.id)
   312→    for s in playbook.pasos[current_idx+1:target_idx]:
   313→        skip_set.add(s.id)
   314→```
   315→
   316→**Bug 2 (CRITICAL): Templates multi-`{{ }}` sólo resuelven el primero.**
   317→
   318→En `executor.py:497-525`, `_resolve_template` usa `re.search` (primer match only) y luego `template.replace(match.group(0), ...)` que reemplaza sólo la primera ocurrencia del match exacto.
   319→
   320→Verificado empíricamente:
   321→```
   322→Input:  "Review {{ a.salida }} and {{ b.salida }}"
   323→Output: "Review <a_value> and {{ b.salida }}"
   324→```
   325→
   326→**Fix:** Usar `re.sub` con una función de reemplazo:
   327→```python
   328→def _resolve_template(self, template, outputs):
   329→    def replace_one(match):
   330→        expr = match.group(1).strip()
   331→        parts = expr.replace("pasos.", "").replace("variables.", "").split(".")
   332→        current = outputs
   333→        for part in parts:
   334→            if isinstance(current, dict):
   335→                part = "output" if part == "salida" else part
   336→                if part in current:
   337→                    current = current[part]
   338→                else:
   339→                    return match.group(0)  # leave as-is
   340→            else:
   341→                return match.group(0)
   342→        return str(current) if not isinstance(current, (dict, list)) else json.dumps(current)
   343→    return self._TEMPLATE_RE.sub(replace_one, template)
   344→```
   345→
   346→**Bug 3 (HIGH): Templates no resuelven paths a través de parallel outputs.**
   347→
   348→`{{ pasos.paralelo.lint.salida }}` → camina `outputs["paralelo"]["lint"]["output"]`. Pero `outputs["paralelo"]` es `{"lint": <lint_output_dict>, "tests": <tests_output_dict>}`. Y `<lint_output_dict>` es directamente el output del specialist (e.g., `{"verdict": "approve", ...}`), no un dict con key `output`.

   351→```python
   352→outputs_map[sub_step.id] = {"output": result.get("output")}
   353→```
   354→Para que `pasos.paralelo.lint.salida` → `outputs["paralelo"]["lint"]["output"]` funcione.
   355→
   356→**Bug 4 (MEDIUM): Templates en lists no se resuelven.**
   357→
   358→En `_resolve_input`, si un valor es una list, se pasa as-is:
   359→```python
   360→else:
   361→    resolved[k] = v  # ← lists, ints, etc.
   362→```

   368→elif isinstance(v, list):

   372→```
   373→
   374→**Bug 5 (HIGH): Template path no encontrado deja el literal `{{ ... }}`.**

   378→return template  # Leave template as-is if not found

   475→## 4. Top 5 mejoras obligatorias antes de launch
   476→
   477→### #1 — Implementar tool-use loop (ReAct) en Specialist.run()
   478→
   479→**Por qué:** Sin esto, los specialists son prompt templates, no agentes. @coder no puede leer código existente, @tester no puede correr tests, @debugger no puede reproducir bugs. Los playbooks de ejemplo (`write-feature-tdd`, `debug-python-issue`) son mentira sin esto.
   480→
   481→**Qué hacer:**
   482→```python
   483→async def run(self, input_data, ctx, *, provider, tool_registry=None):
   484→    messages = [system, user]
   485→    for iteration in range(self.config.max_iterations or 10):
   486→        response = await provider.complete(messages, model=model, tools=tool_schemas)
   487→        if not response.tool_calls:
   488→            break
   489→        messages.append(assistant_msg_with_tool_calls)
   490→        for tc in response.tool_calls:
   491→            result = await tool_registry.get(tc.function.name).execute(tc.function.arguments, ctx)
   492→            messages.append(tool_result_msg)
   493→    return self._parse_output(response)
   494→```
   495→
   496→**Esfuerzo:** 2-3 días. Requiere que ollama y litellm providers pasen tools correctamente y parseen tool_calls.
   497→
   498→### #2 — Conectar el `output_schema` al VerificationLayer y validarlo con pydantic
   499→
   500→**Por qué:** Hoy el schema es decorativo. El sistema reporta `success: True` con outputs que no conforman el schema. Los tests no lo detectan porque el mock devuelve JSON genérico.
   501→
   502→**Qué hacer:**
   503→- En `Specialist.run()`, pasar `response_schema=self.config.output_schema` al provider.
   504→- En `VerificationLayer._validate_structured`, usar pydantic `Type[BaseModel]` en vez de JSON Schema dict.
   505→- En `Specialist._parse_output`, si verification falló, retornar `success=False, error="Schema validation failed: ..."`.
   506→- En `MockLLMProvider`, devolver fixtures schema-conforming por specialist.
   507→
   508→**Esfuerzo:** 1 día.
   509→
   510→### #3 — Unificar el middleware stack en UN lugar
   511→
   512→**Por qué:** Hoy Agent.run() y Specialist.run() ambos envuelven el provider con el stack completo. Resultado: 2 caches, 2 CostGuards (uno useless), 2 VerificationLayers. Confuso, bugs sutiles, doble cost tracking.
   513→
   514→**Qué hacer:**
   515→- Remover el wrapping de `Specialist.run()`.
   516→- El Specialist recibe el provider ya wrapped (del Agent o del Executor).
   517→- El stack se configura en UN lugar: `Agent.__init__` o `PlaybookExecutor.__init__`.
   518→- `Specialist.run()` sólo construye messages, llama `provider.complete()`, parsea output.
   519→
   520→**Esfuerzo:** 0.5 días. Re factor mecánico.
   521→
   522→### #4 — Fix bugs del executor: `saltar_a`, multi-template, parallel output structure
   523→
   524→**Por qué:** Los condicionales y templates son el corazón del DSL. Si no funcionan, los playbooks son mentira.

   526→**Qué hacer:**
   527→- `saltar_a`: skippear intermedios, no el target. (§2.10 Bug 1)

   529→- Parallel outputs: envolver en `{"output": ...}`. (§2.10 Bug 3)

   535→### #5 — Cambiar el default model o añadir JSON post-processing
   536→
   537→**Por qué:** `ollama/llama3.2` 3B no puede producir fiablemente los structured outputs que los system prompts exigen. Combinado con bug #2 (sin validación), el sistema acepta outputs basura silenciosamente.
   538→
   539→**Qué hacer (opción A):** Default a `anthropic/claude-3-5-haiku-20241022` ($0.80/$4.00 per M). Más caro pero structured outputs fiables. Documentar que ollama es para dev/testing.
   540→
   541→**Qué hacer (opción B):** Mantener ollama default pero añadir `_clean_json_response(content)` post-proceso:
   542→```python
   543→def _clean_json_response(content: str) -> str:
   544→    # Strip markdown fences
   545→    content = re.sub(r"^```(?:json)?\s*", "", content.strip())
   546→    content = re.sub(r"\s*```$", "", content.strip())
   547→    # Extract first JSON object if there's prose
   548→    match = re.search(r"\{[\s\S]*\}", content)
   549→    if match:
   550→        return match.group(0)
   551→    return content
   552→```
   553→
   554→**Esfuerzo:** Opción A: 1h (cambio de default + docs). Opción B: 0.5 días + tests.
